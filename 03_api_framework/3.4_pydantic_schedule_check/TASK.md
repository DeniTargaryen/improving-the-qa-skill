## Какая проблема

API (гипотетический, не реальный) возвращает график платежей — общие суммы + список из нескольких месяцев (`entries`). Нужно: а) провалидировать структуру ответа (Pydantic сделает это сам при создании модели из `dict`), б) сравнить конкретные поля с ожидаемым значением — но **не через хардкод заранее посчитанного числа**, а через метод, который сравнивает переданные `expected`-значения с фактическими полями модели.

## Фича — что нужно написать

### 1. `Entry` — один месяц графика

Поля (посмотри форму в `raw_response.py`, там уже есть пример dict — не выдумывай поля с потолка):

- `month: int` — номер месяца по счёту (1, 2, 3...)
- `status: str` — `"planned"` или `"paid"`
- `payment_total: str` — сумма платежа за месяц (строка, не float — деньги как строка/`Decimal`, так принято в реальных API, чтобы не терять точность)
- `payment_debt: str` — остаток долга по этому платежу

Метод `check_values(self, **expected_values) -> tuple[bool, str]`:
- принимает именованные аргументы вида `month=1, status="paid"`
- сравнивает каждое переданное имя с одноимённым полем модели
- если всё совпало — возвращает `(True, "")`
- если что-то не совпало — возвращает `(False, "текст с описанием, что именно не совпало")`

### 2. `Schedule` — весь график

Поля:
- `contract_id: str`
- `entries: list[Entry]` — Pydantic сам провалидирует, что каждый элемент списка соответствует модели `Entry`

Метод `check_values(self, entries: list[dict] | None = None, **expected_values) -> tuple[bool, str]`:
- `expected_values` — проверка полей самого `Schedule` (кроме `entries`)
- `entries` (опционально) — список ожидаемых значений **по каждому месяцу**, по позиции (`entries[0]` сверяется с `self.entries[0]` и т.д.) — через вызов `check_values` у соответствующего `Entry`

## Кто кого вызывает

```python
from raw_response import RAW_SCHEDULE_RESPONSE
from schedule_model import Schedule

schedule = Schedule(**RAW_SCHEDULE_RESPONSE)  # Pydantic валидирует структуру тут

is_valid, error = schedule.check_values(contract_id="abc-123")
assert is_valid, error

is_valid, error = schedule.check_values(
    entries=[{"month": 1, "status": "paid"}, {"month": 2, "status": "planned"}]
)
assert is_valid, error
```

1. `Schedule(**RAW_SCHEDULE_RESPONSE)` — создание модели из `dict`. Если в `raw_response.py` не хватает обязательного поля или тип не совпадает — Pydantic сам бросит `ValidationError` тут же, без единой строки твоего кода.
2. `check_values(...)` — твой отдельный метод, сравнивает то, что реально пришло (`self.<поле>`), с тем, что должно быть (`expected_values`).
3. Тест ловит `(is_valid, error)` и делает `assert is_valid, error` — если что-то не совпало, `error` покажет, что именно.

### Что возвращает

| Функция/метод | Тип возврата | Смысл | Что при ошибке |
|----------------|--------------|-------|------------------|
| `Entry(**dict)` / `Schedule(**dict)` | экземпляр модели | провалидированные данные, доступ через `.month`, `.entries[0].status` и т.д. | `pydantic.ValidationError`, если структура/типы не совпали |
| `Entry.check_values(**expected)` | `tuple[bool, str]` | `(True, "")` если всё совпало, иначе `(False, "текст расхождения")` | не бросает исключение сама — решение об `assert` принимает тест |
| `Schedule.check_values(entries=None, **expected)` | `tuple[bool, str]` | то же самое, но для всего графика + опционально по каждому месяцу | то же |

| Вход | Ожидаемый результат |
|------|------------------------|
| `Schedule(**RAW_SCHEDULE_RESPONSE)` | не падает, `schedule.contract_id` читается |
| `.check_values(contract_id="abc-123")` при реальном `contract_id="abc-123"` в данных | `(True, "")` |
| `.check_values(contract_id="wrong-id")` | `(False, "...")`, в тексте видно `wrong-id` вообще не совпадает с реальным |
| `.check_values(entries=[{"month": 1, "status": "paid"}])` при реальном месяце 1 = `"planned"` | `(False, "...")` |

## Что писать в тестах

Минимум:
1. Валидная структура — `Schedule(**RAW_SCHEDULE_RESPONSE)` не падает, несколько полей читаются напрямую (`.contract_id`, `.entries[0].month`).
2. `check_values` на `Schedule` с верными значениями — `(True, "")`.
3. `check_values` на `Schedule` с одним неверным полем — `(False, ...)`, и в тексте ошибки видно, какое поле разошлось.
4. `check_values` на `Entry` (через `schedule.entries[0]`) отдельно, минимум один позитивный и один негативный кейс.

Без сети, без моков — это чистый unit-тест на бизнес-логику модели, как `check_post_shape` в 2.3/3.3, только на твоём реальном паттерне (Pydantic + сравнение), а не на ручных `dict`.
