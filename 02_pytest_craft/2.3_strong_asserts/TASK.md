# А) `check_post_shape` — заменить `is not None` на `in` + тип — `post_shape.py`

## Какая проблема

Старая привычка (из week0):

```python
def check_post_shape(post: dict) -> None:
    assert post["title"] is not None
```

Здесь две дырки:

1. `post["title"]` — если ключа `"title"` вообще нет в словаре, это `KeyError`, а не понятная проверка «título отсутствует».
2. `is not None` пропускает пустую строку `""`, `0`, `False` — они **не None**, но по смыслу это всё равно битые/подозрительные данные (пост без заголовка, но с пустой строкой вместо заголовка — баг, который эта проверка не найдёт).

## Фича

`check_post_shape(post)` проверяет **4 поля**: `id`, `userId`, `title`, `body`.

Для каждого поля:

1. Ключ **есть** в словаре (`"title" in post`, не `post["title"]` напрямую).
2. Значение **правильного типа**: `id`/`userId` — `int`, `title`/`body` — `str`.
3. Строковые поля (`title`/`body`) — **не пустая строка** после проверки типа.

## Кто кого вызывает

1. Тест собирает `dict` руками (без сети, без API) — валидный или специально сломанный.
2. Тест вызывает `check_post_shape(post)`.
3. Если всё ок — функция **ничего не возвращает** (падать не должна).
4. Если что-то не так — функция **падает** с `AssertionError` (обычный `assert`, не `raise ValueError` — так исторически написано в `checks`, сохраняем стиль).

### Что возвращает

- тип: `None` всегда (даже при успехе)
- смысл: если функция **не упала** — пост валиден по форме
- ошибка/пустой вход: `AssertionError`, если ключа нет, тип не совпадает, или строка пустая

| Вход | Ожидание |
|------|----------|
| `{"id": 1, "userId": 10, "title": "Заголовок", "body": "Текст"}` | не упала (`None`) |
| без ключа `"title"` | `AssertionError` |
| `"title": ""` (пустая строка) | `AssertionError` |
| `"title": 12345` (число вместо строки) | `AssertionError` |
| `"id": "1"` (строка вместо числа) | `AssertionError` |
| `"userId": 0` | **не** падает — `0` валидное значение `userId`, не «пустое» |

**Частая ошибка:** проверить только `in`, забыть про тип, или проверить тип, забыть про пустую строку. Смотри тесты в `test_checks_shape.py` — там есть отдельный кейс на каждую дырку.

# Б) `parametrize` с `ids=` + негативный `parametrize` — `test_checks_parametrize.py`

## Какая проблема

Раньше (0.3/0.4) `parametrize` гонял несколько кейсов, но в отчёте pytest было видно только `test_something[0]`, `test_something[1]` — непонятно, какой конкретно кейс упал без открытия кода теста. На реальном проекте с сотнями кейсов (у тебя на работе ~750) это отдельная боль при разборе упавшего прогона в CI.

`ids=` — способ подписать каждый кейс человекочитаемым именем, которое видно прямо в выводе pytest.

## Фича

Два теста в `test_checks_parametrize.py`:

1. **Позитивный parametrize** — несколько **валидных** `dict`-постов (разные валидные комбинации полей), каждый с понятным `id` (например `"minimal"`, `"long_body"`). Все должны пройти `check_post_shape` без ошибки.
2. **Негативный parametrize** — несколько **невалидных** `dict`-постов (разные виды поломки — можешь взять кейсы из части А и добавить свои), каждый с `id`, описывающим, что именно сломано (например `"missing_title"`, `"empty_body"`, `"userId_as_string"`). Для каждого — `pytest.raises(AssertionError)`.

## Кто кого вызывает

```python
@pytest.mark.parametrize(
    "post",
    [
        {...},  # валидный кейс 1
        {...},  # валидный кейс 2
    ],
    ids=["minimal", "long_body"],
)
def test_valid_posts_pass(post):
    assert check_post_shape(post) is None
```

Для негативного теста — то же самое, но тело теста оборачивает вызов в `with pytest.raises(AssertionError):`.

### Что возвращает (тест, не функция)

| Файл кейсов | Ожидание для каждого |
|-------------|------------------------|
| Позитивный список (≥ 3 кейса) | `check_post_shape` не падает |
| Негативный список (≥ 4 кейса, разные виды поломки) | `check_post_shape` падает `AssertionError` |

**Не пиши** один и тот же кейс дважды под разными `id` — каждый `id` должен описывать **свой** сценарий, иначе теряется смысл `ids=`.
