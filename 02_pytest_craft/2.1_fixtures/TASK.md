# А) Fixture с `yield` и teardown

## Какая проблема

На работе тест часто не должен создавать мусор в системе. Паттерн: тест вызывает фикстуру → фикстура **создаёт** нужные данные (тестовый пост) → отдаёт их тесту → после теста фикстура **сама убирает за собой** (удаляет пост), даже если тест упал.

Без этого через сотню прогонов CI система захламляется тестовыми данными, которые никто не чистит.

## Что такое `yield` в фикстуре (если не трогал раньше)

Обычная фикстура делает `return значение` — и всё, код фикстуры на этом закончился.

Фикстура с `yield` — как будто фикстура **приостанавливается** на `yield`, а не заканчивается:

```python
@pytest.fixture
def имя_фикстуры():
    подготовка()          # выполняется ДО теста
    yield какое_то_значение   # тест получает это значение и работает
    уборка()               # выполняется ПОСЛЕ теста, даже если тест упал
```

Всё, что **до** `yield` — подготовка (setup). Всё, что **после** `yield` — уборка (teardown). pytest сам гарантирует, что код после `yield` выполнится, даже если тест внутри упал с ошибкой.

## Кто кого вызывает

1. Тест объявляет параметр с именем твоей фикстуры (как обычно с фикстурами pytest).
2. pytest перед тестом вызывает твою фикстуру и доходит до `yield`.
3. То, что стоит после `yield`, попадает тесту в параметр.
4. Тест работает с этим значением (например, читает `post["id"]`).
5. После теста pytest возвращается в фикстуру **после строки `yield`** и выполняет уборку.

Внутри фикстуры используй `_api_helpers.create_post(...)` до `yield` и `_api_helpers.delete_post(...)` после `yield`.

### Что возвращает фикстура

- тип: `dict`
- смысл: тело созданного тестового поста (то, что вернул `create_post`, включая `id`)
- ошибка/пустой вход: не применимо — фикстура без параметров, всегда создаёт один и тот же тестовый пост

| Что делает тест | Ожидание |
|------------------|----------|
| Получил `post` из фикстуры | `post` — `dict`, есть ключ `"id"` |
| Тест закончился (успешно или с `assert`-ошибкой) | `delete_post` всё равно вызван (можешь проверить руками через принт/дебаг разово, тестом это не проверить — jsonplaceholder не хранит данные) |

**Не пиши** удаление до `yield` и не забывай `yield` вообще (тогда это будет обычная фикстура без teardown).

# Б) Fixture `scope="module"` — один клиент на весь файл

## Какая проблема

По умолчанию pytest создаёт **новую** фикстуру на **каждый** тест (`scope="function"` — это значение по умолчанию, даже если не пишешь его явно). Если фикстура создаёт что-то тяжёлое (открыть соединение, поднять клиент) — пересоздавать это на каждый тест жалко по времени.

`scope="module"` — фикстура создаётся **один раз** на все тесты в одном файле (`test_b_module_scope.py`), а не пересоздаётся под каждый тест.

## Кто кого вызывает

1. Несколько тестов в одном файле просят одну и ту же фикстуру.
2. Без `scope` pytest создавал бы новый объект под каждый тест.
3. С `scope="module"` pytest создаёт объект **один раз** при первом обращении и отдаёт **этот же** объект всем остальным тестам файла.

### Что возвращает фикстура

- тип: `_api_helpers.ApiClient` (готовый класс, см. `_api_helpers.py`)
- смысл: один клиент, общий на весь модуль теста
- ошибка/пустой вход: не применимо, фикстура без параметров

### Как доказать в тесте, что объект правда один и тот же

Два способа (выбери один или оба):

| Способ | Как проверить |
|--------|----------------|
| Через `id()` | В двух разных тестах сохранить `id(client)` в модульную переменную/список и сравнить, что оба раза `id` одинаковый |
| Через счётчик `calls` | `ApiClient.calls` растёт с каждым вызовом `.get(...)`. Если тест 1 вызвал `.get(...)` один раз, а тест 2 — тоже один раз, и после теста 2 `client.calls == 2` (а не `1`) — значит клиент общий, не пересоздан |

| Сценарий | Ожидание |
|----------|----------|
| Тест 1 и тест 2 в одном файле оба используют фикстуру | `id(client)` одинаковый в обоих тестах |
| Тест 1 вызвал `client.get(...)` раз, тест 2 — ещё раз | `client.calls == 2` во втором тесте |

**Частая ошибка:** написать `scope="module"`, но по факту так и не проверить это тестом — тогда фикстура технически верная, но упражнение не сдано, потому что ты ничего не доказал pytest'ом.

# В) Фабрика фикстур

## Какая проблема

Иногда одного объекта из фикстуры мало — тесту нужно создать **несколько** постов с разными данными внутри самого теста (не заранее, а по ходу теста, возможно даже разное количество в разных тестах).

Обычная фикстура отдаёт готовое значение один раз. Фабрика — фикстура, которая отдаёт **функцию**, и тест сам вызывает эту функцию столько раз, сколько нужно.

## Кто кого вызывает

1. Тест просит фикстуру-фабрику как обычно (параметром).
2. Фикстура возвращает не `dict`, а `Callable` — функцию, которую можно вызывать.
3. Тест сам вызывает эту функцию (например, три раза подряд с разными `title`), и каждый вызов создаёт новый пост через `_api_helpers.create_post`.

```python
def test_example(make_post):
    p1 = make_post(title="один")
    p2 = make_post(title="два")
```

### Что возвращает

- фикстура возвращает: `Callable[..., dict]` — функцию, а не готовые данные
- вызов этой функции возвращает: `dict` — тело одного созданного поста (как `create_post`)
- ошибка/пустой вход: если вызвать без аргументов — реши сам разумные значения по умолчанию (например, `title` по умолчанию непустая строка), это не должно падать

| Вызов | Ожидание |
|-------|----------|
| `make_post()` | `dict` с `"id"` внутри |
| `make_post(title="A")`, потом `make_post(title="B")` | два разных вызова `create_post`, оба вернули `dict`, тест может собрать их в список и проверить, что оба созданы (например длина списка `== 2`) |

**Не пиши** `return сразу_список_из_трёх_постов` — это не фабрика, это обычная фикстура с побочным эффектом. Фабрика — это когда фикстура отдаёт именно **функцию**, а решение «сколько раз вызвать» — за тестом.
