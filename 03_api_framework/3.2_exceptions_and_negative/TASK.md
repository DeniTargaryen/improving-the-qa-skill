# Блок 3.2 — Свои исключения в `BaseApi` + негативный тест (Track B)

**Зачем этот блок реально нужен:** «напиши клиент, который кидает свою ошибку вместо голого assert» — частый вопрос именно к AQA (не просто «умеешь Python», а «умеешь строить тест-фреймворк»). Закрывает долг из **1.2**, где `ApiError`/`NotFoundError` были пустыми классами без применения — здесь они наконец реально работают в коде клиента. Разбор рынка — `docs/sonnet_reviews/2026-08-12-task-self-review-vs-real-interviews.md`.

Самодостаточно: своя копия клиента (`negative_api.py`), не week0, не `02_pytest_craft`.

```bash
python -m pytest 03_api_framework/3.2_exceptions_and_negative -v
```

## Файлы

| Файл | Кто пишет | Что внутри |
|------|-----------|------------|
| `api_errors.py` | **ты** | `ApiError`, `NotFoundError` (как в 1.2) |
| `negative_api.py` | **ты** (рефакторинг `get`) | вместо `assert` — `raise` твоих классов |
| `test_exceptions_negative.py` | **ты** | тесты на 404 и на твои исключения |

**Почему файлы называются `negative_api.py`/`api_errors.py`, а не `base_api.py`/`exceptions.py`:** в репозитории уже есть одноимённые модули (1.1, 1.2, другие блоки недели 3) — без пакетов с `__init__.py` общий прогон pytest по всему репо закэшировал бы только первый импортированный модуль с таким именем и подставил его во всех остальных местах (тихий баг, не твоя ошибка). Класс внутри всё равно называется `BaseApi`.

## Какая проблема

Открой `negative_api.py` — там сейчас `assert r.status_code == 200, f"..."`. Это работает, но:

1. Если статус `404` (реально нет такой сущности) и если статус `500` (сервер упал) — тест видит **одинаковую** ошибку (`AssertionError` с текстом). На реальном проекте это разные ситуации: 404 — «данных нет, это нормальный кейс для проверки», 500 — «сервер сломан, это баг».
2. `pytest.raises(AssertionError)` — слишком общий тип, не показывает **что именно** пошло не так по смыслу API.

## Фича

1. В `api_errors.py`: `ApiError(Exception)` и `NotFoundError(ApiError)` — как в 1.2, только теперь используются реально.
2. В `negative_api.py`, метод `get`: вместо `assert r.status_code == 200, ...` —

```text
если status_code == 404: raise NotFoundError(текст)
если status_code != 200 (и не 404): raise ApiError(текст)
если status_code == 200: return r.json() как обычно
```

## Кто кого вызывает

1. Тест вызывает `api.get("/posts/99999999")` — несуществующий пост на jsonplaceholder (там он реально отвечает `404`).
2. Внутри `get` видит `status_code == 404` → `raise NotFoundError(...)`.
3. Тест ловит: `with pytest.raises(NotFoundError): api.get(...)`.

Для проверки `ApiError` можно замокать ответ с другим плохим статусом (например через `unittest.mock.patch` на `requests.get`, ты это уже умеешь из 2.2) — реальный jsonplaceholder почти всегда отвечает `200`/`404`, других статусов от него не добиться без мока.

### Что возвращает `get` после рефакторинга

| Статус ответа | Действие | Тип |
|---------------|----------|-----|
| `200` | `return r.json()` | `dict` |
| `404` | `raise NotFoundError(...)` | исключение, не `dict` |
| любой другой «не 200» | `raise ApiError(...)` | исключение, не `dict` |

| Вызов | Ожидание |
|-------|----------|
| `api.get("/posts/1")` (существует) | вернул `dict` |
| `api.get("/posts/99999999")` (не существует) | `pytest.raises(NotFoundError)` |
| замоканный ответ со статусом `500` | `pytest.raises(ApiError)` |

**Важно:** `NotFoundError` — это **подкласс** `ApiError` (наследование из 1.1/1.2). Значит `except ApiError` поймает и `NotFoundError`, но `except NotFoundError` не поймает обычный `ApiError`. В тесте проверяй конкретный тип, который ждёшь (`pytest.raises(NotFoundError)` для 404-кейса, не `ApiError`).
