### Суть претензии
- Непонятно, зачем оборачивать `BaseApi` в ещё один класс с **захардкоженным URL**.
- Это бьётся с интуицией ученика: API-клиент как раз для **универсальности** (`BaseApi(base_url)`), а не для хардкода host внутри наследника.
- Описание/`super` сначала были даны копипастой без понимания; даже после разжёвки остаётся вопрос «кто в здравом уме так пишет».

### Контекст коуча
- Пункт из плана post-week0 §1.1 как минимальный drill на `super()` / наследование.
- На работе ученика паттерн ближе: `BaseApi(base_url=...)` + функции-эндпоинты, без узкого наследника под один host.
- Независимое ревью ранее уже резало лишний `PostsApi`; этот пункт — соседняя зона риска «OOP ради OOP».

## Дополнение 07.08.2026 — блок 1.2 и качество TASK

- В 1.2 `ApiError`/`NotFoundError` и `safe_divide` **не связаны** в одном сценарии → ученик закономерно ждал применения своих ошибок в `safe_divide`. Лучше один сквозной мини-кейс (например safe_get → raise NotFoundError) или явно в TASK жирным: «это два независимых упражнения».

- Ученик: если логика formal-wrong, но текущие тесты зелёные — коучу говорить прямо: «тесты узкие, кейс X всё равно сломан», не только «не двигаем».

**Опыт ученика:** ~**2 часа**, с огромным трудом. Оценка: **худшая глава/задание** в треке на текущий момент.

### Что бесило
- Тупые/кривые описания в TASK: этажи `@retry(times=3)`, кто кого вызывает, что не про время/`sleep`.
- Куча непонятных слов и абстракций без расшифровки; коуч не держал модель «что ученик уже знает / что нет» (`with`, классы со вчера, `except as e` нюанс Python 3).
- Коуч давал советы с дырами в знании Python (например `raise e` после `except` → `UnboundLocalError`, потому что `e` стирается) и заставлял ученика **править ошибки коуча по 5 раз**.
- Рассинхрон «верь TASK (А→Б→В)» vs советы коуча (чинить `retry` раньше времени / копипаста каркаса).
- Ощущение: «это пиздец, а не учёба».
