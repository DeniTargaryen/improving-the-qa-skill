## 1. Дыры после Week 0 (что обычно пропускают)

Прямо по пунктам — где Week 0 даёт ложное чувство готовности:

1. **Классы = один тривиальный `BaseApi` с одним атрибутом.** `self`, `__init__`, наследование, `@classmethod`/`@staticmethod`, dunder-методы (`__eq__`, `__repr__`) не тронуты вообще. На собесе часто просят «напиши класс с методом», и текущего опыта (только `self.base_url = ...`) не хватит.
2. **Нет моков.** Все тесты 0.4 бьют в реальный jsonplaceholder. Топовый вопрос AQA-собеса — «как протестировать функцию, которая дёргает API, без реальной сети» (`unittest.mock`, `requests-mock`/`responses`). Это не задето вообще.
3. **Обработка ошибок — только `assert` внутри `BaseApi.get`.** Нет custom exceptions, нет `try/except`, нет ветвления по статусу (404 vs 500 vs таймаут). Ассерт — не то, что просят реализовать на interview («напиши клиент, который кидает свою ошибку»).
4. **Ассерты в `checks` слабые.** `check_post_shape` проверяет `is not None`, а не наличие ключа (`in`) и не тип значения. `is not None` пропустит баг, если поле — пустая строка/0/`False`, а тип вообще не проверяется. Это стоит явно исправить, а не тащить привычку дальше.
5. **Фикстуры — только «отдать строку».** Ни `yield`+teardown, ни `scope=`, ни фабрики фикстур не практиковались, хотя по профилю ученика реальная работа была именно со «сложными setup/teardown заявок» — но это мышечная память, не осознанное умение объяснить и написать с нуля под чужой TASK.md.
6. **`BaseApi` умеет только `GET`.** Ни `POST`/`PUT`/`PATCH`/`DELETE`, ни переиспользуемой `requests.Session`, ни заголовков авторизации — а «напиши клиент для CRUD» на лайвкодинге встречается регулярно.
7. **Питон-тривиа не проверялась.** `is` vs `==`, mutable default argument, shallow vs deep copy, `*args`/`**kwargs`, list/dict comprehensions — классические быстрые вопросы в начале технического собеса, которые легко потерять на нервах без предварительного повторения.
8. **Нет декораторов и контекстных менеджеров своими руками.** Ученик использует `@pytest.fixture`/`@pytest.mark.parametrize`, но не писал свой декоратор или `__enter__`/`__exit__` — а вопрос «как работает `@pytest.fixture` изнутри» на собесах по pytest не редкость.
9. **Нет негативных API-тестов и валидации структуры ответа.** Только happy path (получить пост по id). Ни 404, ни битого тела, ни проверки схемы через `jsonschema` или ручную функцию.
10. **Allure не тронут вообще** (сознательно отложен из Week 0) — но раз это часть стека прошлой работы, к финалу подготовки минимум `allure.step` на паре тестов нужен, иначе на вопрос «расскажи про Allure» будет пусто.

Это и есть скелет недель 1–4 ниже.

## Неделя 1 — `01_python_core`

**Гейт входа:** 0.5 (interview voice) сдан.
**Гейт выхода:** весь блок 1.x сдан, включая drill 1.4, прежде чем открывать `02_pytest_craft`.

### 1.1 OOP-минимум для AQA (Track A)

**Цель:** уверенно писать `__init__`/`self`/методы/наследование — без этого дальше нечего усложнять `BaseApi`.

- **`Account`** — класс с `__init__(self, owner, balance=0)`, методами `deposit`/`withdraw`. Что делает: меняет `self.balance`, `withdraw` не даёт уйти в минус.
- **`Rectangle`** — методы обычные + `@classmethod from_square(side)` + `@staticmethod is_valid(width, height) -> bool`. Что возвращает: `from_square` — новый `Rectangle`, `is_valid` — `bool`, ничего не создавая.
- **`Money`** — dunder-методы `__eq__`, `__repr__`. Что возвращает: `__eq__` — `bool` сравнения по сумме и валюте, `__repr__` — читаемую строку для дебага/сравнения в тестах.
- **`JsonPlaceholderApi(BaseApi)`** — наследник существующего `BaseApi` из 0.4 с захардкоженным `base_url` по умолчанию. Что делает: `__init__` без аргументов, вызывает `super().__init__(...)`.

### 1.2 Исключения вместо голого assert (Track A → B)

**Цель:** подготовить базу для 3.3 (переписать `BaseApi` на свои ошибки).

- **`ApiError(Exception)` / `NotFoundError(ApiError)`** — своя иерархия исключений. Что делает: ничего сверх стандартного `Exception`, кроме имени класса (для `except ApiError` и `except NotFoundError` по отдельности).
- **Функция-тренировка `safe_divide(a, b)`** — Track A. Что возвращает: число, либо кидает `ZeroDivisionError` с понятным сообщением через `raise ... from ...`. Цель — попрактиковать `try/except/else/finally` и порядок их выполнения.
- **Мини-рефакторинг (Track B, по желанию сразу или переносится в 3.3):** `BaseApi.get` кидает `NotFoundError` при 404 и `ApiError` при остальных «не 200» вместо общего `assert`.

### 1.3 Декораторы и context manager своими руками (Track A)

**Цель:** понять механику `@pytest.fixture`/`@pytest.mark` изнутри, чтобы на собесе не плавать в вопросе «как это работает».

- **`retry(times=3)`** — декоратор-фабрика. Что делает: оборачивает функцию, повторяет вызов при исключении до `times` раз, последнее исключение пробрасывает дальше.
- **`timeit`** — простой декоратор. Что делает: печатает время выполнения обёрнутой функции, возвращает её результат без изменений.
- **`Timer`** — класс context manager (`__enter__`/`__exit__`). Что возвращает: объект с атрибутом `elapsed` после выхода из `with`.

### 1.4 Drill — питон-тривиа (устно + мини-код)

**Формат:** быстрые вопросы + 1–2 строки кода на исправление, без новых концепций.

- `is` vs `==` — когда `is` даёт неожиданный `True`/`False`.
- Mutable default argument — почему `def f(x=[])` — ловушка, как чинить.
- Shallow vs deep copy — предсказать поведение `copy()` на списке списков.
- `*args`/`**kwargs` — написать функцию-обёртку, которая просто прокидывает аргументы дальше (без бизнес-логики).

**Гейт:** устно объясняет все 4 пункта + все TASK.md недели 1 сданы → открываем неделю 2.

## Неделя 2 — `02_pytest_craft`

**Гейт входа:** неделя 1 полностью сдана.
**Гейт выхода:** блок 2.x сдан → открываем `03_api_framework`.

### 2.1 Фикстуры как на работе — осознанно (Track B)

**Цель:** закрыть разрыв между «фикстура отдаёт строку» (0.3) и настоящими setup/teardown, которые уже есть в мышечной памяти с прошлой работы, но не тренировались с нуля.

- **Fixture с `yield` и teardown** — создаёт тестовый пост через API перед тестом, удаляет после. Что возвращает: `dict` созданного поста в тело теста; после `yield` — блок очистки.
- **`scope="module"` фикстура** — один общий клиент/сессия на все тесты модуля. Что возвращает: тот же объект во всех тестах модуля (проверяется через `id()` или счётчик вызовов).
- **Фабрика фикстур** — фикстура возвращает функцию, которая создаёт N постов с разными параметрами. Что возвращает: `Callable`, вызов которой создаёт и возвращает `dict`/`list[dict]`.

### 2.2 Моки внешних вызовов (Track A → B) — приоритет №1 этого месяца

**Цель:** самый частый пробел вчерашних мануальщиков — не уметь тестировать код без реальной сети.

- **`unittest.mock.patch`** на изолированной функции (не трогая `posts.py`) — Track A, готовый тест уже мокает вызов, ученик пишет функцию под него. Что делает функция: вызывает переданный клиент/зависимость, возвращает её результат без изменений.
- **Переписать один тест из 0.4 на mock** вместо реального похода в сеть (мокается `requests.get` или `BaseApi.get`). Что проверяет тест: что функция вызвала мок с нужными аргументами и вернула то, что мок отдал.
- **(опционально) `requests-mock`/`responses`** — короткое знакомство: один тест на этой библиотеке вместо ручного `patch`, для сравнения подходов.

### 2.3 Сильные ассерты и parametrize (усиление дыры из 0.4)

**Цель:** переписать привычку `is not None` на `in` + проверку типа — иначе баг с пустой строкой/нулём пролетит незамеченным.

- **Переписать `check_post_shape`** (Track B, тот же файл из 0.4) — вместо `x is not None` использовать `"title" in post` и `isinstance(post["title"], str)` и т.д. Что возвращает: по-прежнему `None`, но падает точнее и раньше.
- **`parametrize` с `ids=`** — тот же список кейсов из 0.3/0.4, но с читаемыми `ids`, чтобы в отчёте pytest было видно, какой кейс упал.
- **Негативный parametrize** — список «плохих» post_id/данных → ожидаем `raises` (или `NotFoundError` из 1.2/3.3), одним тестом на несколько кейсов.

### 2.4 Drill — маркеры и конфиг pytest

- Зарегистрировать кастомный маркер в `pytest.ini`, объяснить зачем (иначе warning).
- Прогнать `-m smoke` и `-k <подстрока>`, объяснить разницу.
- Устно: где ищет `conftest.py` pytest (discovery), почему fixture из корневого `conftest.py` видна во вложенных папках.

**Гейт:** 2.1–2.3 сданы, 2.4 пройден устно → открываем неделю 3.

## Неделя 3 — `03_api_framework`

**Гейт входа:** неделя 2 полностью сдана.
**Гейт выхода:** блок 3.x сдан → неделя 4 (буфер) или финал.

### 3.1 `BaseApi` — полный CRUD (Track B)

**Цель:** «напиши клиент для CRUD» — частый лайвкодинг на AQA-собесе.

- **`post(self, path, json, expected_status=201) -> dict`** — что возвращает: `dict` тела ответа, аналогично существующему `get`.
- **`put` / `patch`** — по аналогии, разница только в HTTP-методе и обычно `expected_status=200`.
- **`delete(self, path, expected_status=200) -> None`** — что возвращает: ничего, только проверка статуса.
- **Тесты на jsonplaceholder**: создать пост → обновить → удалить, используя все новые методы (jsonplaceholder не хранит данные по-настоящему, но валидирует контракт запроса/ответа — это нормально и достаточно для тренировки).

### 3.2 Негатив и схема ответа (Track B)

**Цель:** закрыть «только happy path» из 0.4.

- **Тест на 404** — запрос несуществующего поста, ожидаемое поведение уже определено в 1.2/3.3 (своя ошибка, не `assert`).
- **Ручная функция `validate_post_schema(post: dict) -> None`** (или через `jsonschema`, если решите её подключить) — что делает: падает с понятной ошибкой, если не хватает ключа или тип не совпадает с ожидаемым.
- **Тест на «битый» ответ** — можно замокать (см. 2.2/3.4) ответ без обязательного поля и проверить, что `validate_post_schema` действительно падает.

### 3.3 Свои исключения в `BaseApi` (Track B, закрывает 1.2)

**Цель:** заменить `assert` в `get`/`post`/`put`/`delete` на осмысленные исключения.

- **Рефакторинг `BaseApi`**: при «не ожидаемый статус» кидать `NotFoundError` (404) или `ApiError` (остальное) вместо `assert ... , f"..."`.
- **Тесты на исключения**: `pytest.raises(NotFoundError)` / `pytest.raises(ApiError)` вместо проверки текста ассерта.

### 3.4 Unit-тесты слоёв на моках (Track B, закрывает 2.2 на практике)

**Цель:** `checks`/`posts.py` тестируются без сети вообще — типичное требование «покрой юнит-тестами бизнес-логику клиента».

- **Тест `check_post_shape`** на руками собранном `dict` (валидном и невалидном) — без единого HTTP-запроса.
- **Тест `get_post`/`get_posts`** с замоканным `BaseApi.get` — что возвращает: тест проверяет, что функция вернула ровно то, что отдал мок, и вызвала его с правильным `path`.

**Гейт:** 3.1–3.4 сданы → неделя 4 (если есть время) либо переход к финальному чек-листу.

## 4. Чего НЕ делать (overengineering)

Прямо и конкретно:

- **Не городить `PostsApi`/`UsersApi`-классы поверх `BaseApi`.** Один `BaseApi` + функции-эндпоинты — как уже зафиксировано в 0.4, это правильный уровень для лайвкодинга. Наследник в 1.1 (`JsonPlaceholderApi`) — это упражнение на ООП, а не новый архитектурный слой поверх реальных тестов.
- **Не строить Page Object Model / UI-слой.** Цель — API + ASAP, Selenium/Playwright не нужны, пока явно не попросят на конкретном собесе.
- **Не тащить `jsonschema`, `pydantic` или ORM «про запас».** Ручной валидатор в 3.2 достаточен; если код позволяет — можно один раз показать `jsonschema` для галочки «знаю», но не переписывать всё на неё.
- **Не делать полноценный CI/CD (GitHub Actions и т.д.).** Не входит в цель «работа ASAP»; если спросят на собесе — это тема для устного ответа (0.5/4.3), не для отдельного блока.
- **Не подключать Allure раньше недели 4 и не более 2–3 шагов/аттачей.** Задача — «умею показать, что знаю», а не переписать все тесты под Allure-отчёты.
- **Не писать общий `AbstractApi`/интерфейсы/протоколы «на будущее».** Один реальный `BaseApi` без предварительной абстракции — преждевременное обобщение под несуществующую вторую реализацию.
- **Не трогать async/await**, если это не всплывёт как явный вопрос на конкретном собесе — не входит в типичный AQA screen уровня "ASAP, не FAANG-hard".
- **Не тащить DB/SQLAlchemy/фикстуры к реальной БД.** Профиль ученика и так силён в setup/teardown к БД с прошлой работы — тренировать это заново не нужно, максимум — устный ответ, если спросят.
