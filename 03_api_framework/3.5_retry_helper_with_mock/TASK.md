## Какая проблема

`retry_call` оборачивает вызов какой-то операции, которая может упасть от временной проблемы (например, сеть/сервис на секунду не готов). Она повторяет вызов до `max_attempts` раз, с паузой `time.sleep(retry_delay)` между попытками, и в конце либо возвращает результат, либо кидает `RetryError`.

**Проблема для теста:** если тестировать это на реальной нестабильной зависимости — тест будет случайным (то падает, то нет) и медленным (реальные секунды `sleep`). Нужно: а) подставить **предсказуемо нестабильную** зависимость через `unittest.mock` (`side_effect` со списком — сначала ошибки, потом успех), б) убрать реальное ожидание, тоже через `patch` на `time.sleep`.

## Кто кого вызывает

```python
from unittest.mock import Mock, patch

from retry_helper import RetryError, retry_call


def test_retry_call_succeeds_on_third_attempt():
    flaky_operation = Mock(side_effect=[ValueError("temp"), ValueError("temp"), "ok"])

    with patch("retry_helper.time.sleep"):
        result = retry_call(flaky_operation, max_attempts=3, retry_delay=1)

    assert result == "ok"
    assert flaky_operation.call_count == 3
```

1. `Mock(side_effect=[...])` — при каждом вызове `flaky_operation()` отдаёт следующий элемент списка по очереди; если элемент — исключение, оно **бросается**, если обычное значение — **возвращается**.
2. `patch("retry_helper.time.sleep")` — подменяет `time.sleep` **в модуле `retry_helper`**, не глобально `time.sleep` — вспомни правило из 3.2: `patch` там, где имя **используется**, а не где определено. `retry_helper.py` делает `import time` и вызывает `time.sleep(...)`, значит патчить нужно `"retry_helper.time.sleep"`.
3. `retry_call` вызывает `flaky_operation()` внутри, ловит исключение, если попытка не последняя — «спит» (но `sleep` замокан, поэтому реально не ждёт), пробует снова.
4. Тест проверяет: а) финальный результат, б) сколько раз реально вызвалась `flaky_operation` (`call_count`).

### Что возвращает

| Функция | Мокаем | Что проверяем |
|---------|--------|-----------------|
| `retry_call(op, max_attempts=3, retry_delay=...)` при `op` = Mock с `side_effect=[ошибка, ошибка, "ok"]` | `op` (через `Mock`) + `retry_helper.time.sleep` | вернула `"ok"`; `op.call_count == 3` |
| `retry_call(op, max_attempts=3, ...)` при `op` = Mock, который падает **всегда** (`side_effect=ValueError("x")`, без списка — упадёт на каждом вызове) | то же | `pytest.raises(RetryError)`; `op.call_count == max_attempts` (не больше и не меньше) |
| `retry_call(op, max_attempts=3, ...)` при `op` = Mock, который сразу возвращает значение (`return_value="ok"`, без ошибок вообще) | `retry_helper.time.sleep` (на всякий случай, чтобы тест не спал, даже если попытка одна) | вернула `"ok"`; `op.call_count == 1` (без единого повтора) |

## Что писать в тестах

Минимум три теста — по одной строке таблицы выше: «падает N раз, потом успех», «падает всегда → `RetryError`», «успех с первого раза → без повторов». В каждом — обязательно замокан `time.sleep` (иначе тест 2 и 3 может случайно долго спать, тест 1 — точно будет спать реальные секунды между попытками).

# Зачем весь блок (одна фраза)

Тестирование retry/backoff-логики без реального ожидания и без флаки-реальной сети — частый практический навык на живом собесе AQA («как бы вы протестировали функцию с повторными попытками»), а не абстрактная тема «декораторы ради декораторов»; здесь тот же принцип retry, который тебе тяжело давался в 1.3, но теперь с другой стороны — не пишешь механику сам, а учишься её **проверять**, что на практике встречается чаще, чем написание retry с нуля.
