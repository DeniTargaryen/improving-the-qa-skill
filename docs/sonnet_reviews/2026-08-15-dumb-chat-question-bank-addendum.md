## G. Твой реальный фреймворк — архитектура и решения (8 вопросов)

**46.** Расскажите на примере, как у вас разделены слои `api`/`helper`/`models` в фреймворке — кто кого вызывает.

Эталон: `api`-слой — самый нижний, тонкие функции-обёртки над HTTP-эндпоинтами (собрать запрос, вызвать `BaseApi`, вернуть ответ), без бизнес-логики. `helper`-слой — выше, вызывает функции `api`-слоя, добавляет бизнес-оркестрацию (несколько вызовов подряд, ретраи, ожидания, проверки статусов между шагами). `models` — Pydantic-схемы, в которые оборачивается ответ API для валидации структуры и удобного доступа к полям. Тесты обращаются к `helper`, а не прямо к `api`, чтобы не дублировать оркестрацию в каждом тесте.

**47.** Зачем нужен отдельный слой `helper`, если можно было вызывать `api`-клиент прямо из теста?

Эталон: если тест вызывает `api` напрямую, то любая многошаговая бизнес-операция (например «создать → подождать готовности → проверить статус») дублируется в каждом тесте, который её использует. `helper` инкапсулирует это один раз — тест читается как бизнес-сценарий («создали транш, проверили лимиты»), а не как последовательность HTTP-вызовов, и правки логики (например добавить ретрай) делаются в одном месте, а не в десятке тестов.

**48.** Почему для валидации ответа используется отдельная Pydantic-модель, а не просто проверка ключей в `dict` внутри теста?

Эталон: Pydantic-модель описывает контракт один раз (обязательные/опциональные поля, типы, вложенность) и валидирует его автоматически при создании объекта из ответа — если структура не совпала, ошибка выскочит сразу и явно, без ручных `if "field" not in response`. Плюс модель даёт удобный доступ через атрибуты (`schedule.entries[0].status`) и можно повесить на неё свои методы (`check_values`) для сравнения с ожидаемым — переиспользуемо между тестами.

**49.** Зачем вообще нужен `pytest-xdist` (`-n 10` и подобное) и что при этом нужно учитывать в тестах?

Эталон: `pytest-xdist` запускает тесты параллельно в нескольких процессах, чтобы весь набор проходил быстрее (особенно важно для e2e с реальными HTTP-вызовами, где один тест может идти секунды). Учитывать: тесты не должны зависеть друг от друга и делить общее мутируемое состояние (общий тестовый пользователь, общий файл, общая запись в БД) — иначе параллельный запуск даёт флаки; для этого используют изоляцию данных (каждый тест генерирует свои уникальные сущности) или группировку тестов, которые обязаны идти в одном процессе (например через `--dist loadgroup` и маркировку группы).

**50.** Как объяснить на собесе фразу «мокаем внешние зависимости», если у вас на практике это управляется через специальный заголовок/флаг, переключающий сервис в тестовый режим, а не через отдельный процесс типа Mountebank?

Эталон: это тоже валидный уровень мокирования внешних зависимостей — просто управление находится не в тесте напрямую (поднять свой mock-сервер), а на стороне тестируемого сервиса (специальный заголовок в запросе переключает его на использование заранее подготовленных фейковых ответов от внешних систем вместо реальных вызовов). Суть та же: тестируемый код получает предсказуемый, управляемый ответ вместо нестабильной реальной внешней системы, просто конфигурация мока — часть контракта самого API, а не отдельная инфраструктура, которую поднимает тест.

**51.** Зачем в реальном фреймворке хелпер оборачивает вызов в retry (повторные попытки), если API и так должен отвечать сразу?

Эталон: некоторые операции асинхронны на стороне сервера — например, лимиты или график платежей могут обновиться не мгновенно после операции, а через некоторое время (обработка в фоне). Прямая проверка сразу после операции может увидеть старое состояние не потому что тест неправильный, а потому что сервер ещё не успел. Retry с паузой между попытками даёт системе время обновиться, вместо того чтобы тест был случайно нестабильным (flaky) из-за жёсткой привязки к точному времени ответа.

**52.** Почему тела денежных сумм в ответах API передаются как строки (`"5000.00"`), а не как числа (`float`)?

Эталон: `float` не точен для денежных вычислений (ошибки округления на двоичном представлении), а деньги нельзя терять/добавлять из-за округления. Строка (или `Decimal` при работе с ней в коде) сохраняет точное десятичное значение без искажений; при сравнении такие значения нормализуют через `Decimal` до сравнения, а не сравнивают строки напрямую (иначе `"5000.00"` и `"5000"` считались бы разными, хотя это одна и та же сумма).

**53.** Как бы вы объяснили интервьюеру, почему в фреймворке несколько разных `api`-клиентов (например под разные внешние сервисы), а не один универсальный?

Эталон: разные внешние сервисы имеют разные базовые URL, разные контракты эндпоинтов и иногда разную аутентификацию — единый клиент на все сервисы либо превратился бы в мешанину условий по имени сервиса, либо потерял бы специфику каждого API. Отдельный клиент на сервис даёт понятную границу ответственности (один файл = один внешний сервис), упрощает поддержку при изменении контракта одного сервиса без риска задеть остальные.
