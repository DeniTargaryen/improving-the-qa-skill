## Список вопросов и эталонов

### A. Python — типы, mutable/immutable, аннотации (8 вопросов)

**1. [ДОЛГ]** Какие базовые типы данных в Python вы можете назвать? Назовите как можно больше, не только `int`/`str`/`float`.

Эталон: `int`, `float`, `complex`, `str`, `bool`, `NoneType`, `list`, `tuple`, `dict`, `set`, `frozenset`, `bytes`/`bytearray`. `bool` — фактически подтип `int` (`True == 1`). `None` — единственное значение типа `NoneType`. Чаще всего забывают именно `None`, `bool`, `set`, `frozenset`.

**2. [ДОЛГ]** Разделите основные типы на изменяемые (mutable) и неизменяемые (immutable). Объясните разницу своими словами.

Эталон: immutable — `int`, `float`, `bool`, `str`, `tuple`, `frozenset`, `bytes`, `None` (после создания объект нельзя изменить «на месте» — операция создаёт новый объект). Mutable — `list`, `dict`, `set` (можно менять содержимое тем же объектом в памяти: `append`, `d[k]=v`, `add`). Проверка на практике: у mutable-объекта `id()` не меняется после изменения содержимого, у immutable — любая «модификация» это новый объект с новым `id()`.

**3.** Почему `tuple` считается неизменяемым, а `list` — изменяемым, если оба — последовательности?

Эталон: у `list` есть методы, меняющие содержимое на месте (`append`, `remove`, `sort`, `__setitem__`), у `tuple` таких методов нет — после создания элементы и длина зафиксированы. Если внутри `tuple` лежит mutable-объект (например `list`), сам этот вложенный объект всё равно можно менять — неизменяемость `tuple` касается только его собственной структуры (ссылок на элементы), а не содержимого элементов.

**4. [ДОЛГ]** В сигнатуре `def f(name: str) -> dict:` — что аннотирует `str`, а что `dict`? Проверяет ли Python эти типы во время выполнения?

Эталон: `name: str` — ожидаемый тип **аргумента**; `-> dict` — ожидаемый тип **возвращаемого значения**. Python по умолчанию **не проверяет** аннотации в runtime — это подсказка для человека, IDE и внешних инструментов (`mypy`, `pyright`). Функция спокойно выполнится, даже если передать `int` вместо `str`.

**5. [ДОЛГ]** Чем отличается `is` от `==`? Приведите пример, где они дают разный результат.

Эталон: `==` сравнивает значения (вызывает `__eq__`), `is` сравнивает идентичность объектов — один и тот же объект в памяти (`id()` совпадает). Пример: `a = [1, 2]; b = [1, 2]` → `a == b` даёт `True`, `a is b` даёт `False` (разные объекты с одинаковым содержимым). Для `None` всегда использовать `is None`, а не `== None`.

**6. [ДОЛГ]** Что не так с `def f(x=[]): x.append(1); return x` при повторных вызовах без аргумента?

Эталон: значение по умолчанию (`[]`) создаётся один раз при определении функции, а не при каждом вызове — все вызовы без аргумента делят один и тот же mutable-объект. Второй вызов вернёт `[1, 1]`, третий — `[1, 1, 1]` и так далее. Правильно: `x=None`, а внутри `if x is None: x = []`.

**7. [ДОЛГ]** Чем `.copy()` (shallow copy) отличается от `copy.deepcopy()`? Когда shallow copy «подводит»?

Эталон: `.copy()` создаёт новый внешний объект, но вложенные mutable-объекты (например списки внутри списка) остаются общими ссылками с оригиналом. `deepcopy` рекурсивно копирует всё вложенное дерево. Пример: `rows = [[1,2],[3,4]]; new = rows.copy(); new[0][0] = 99` — после этого `rows[0][0]` тоже станет `99`, потому что `rows[0]` и `new[0]` — один и тот же объект.

**8.** Чем `set` отличается от `frozenset` и когда нужен `frozenset`?

Эталон: `set` — изменяемое множество уникальных элементов (`add`/`remove`), `frozenset` — его неизменяемый аналог. `frozenset` нужен, когда множество должно быть hashable — например, использоваться как ключ `dict` или как элемент другого `set`.

### B. pytest (8 вопросов)

**9.** Что такое `scope` у фикстуры pytest и какие значения он принимает?

Эталон: `scope` определяет, как часто пересоздаётся фикстура: `function` (по умолчанию, на каждый тест), `class`, `module`, `package`, `session` (один раз на весь прогон). Чем шире scope — тем реже пересоздание, но выше риск нежелательного шаринга состояния между тестами.

**10.** Что делает `yield` внутри фикстуры и зачем он нужен вместо `return`?

Эталон: `yield` делит фикстуру на «setup» (код до `yield`) и «teardown» (код после `yield`). Значение до `yield` передаётся в тест, а код после `yield` выполняется после теста — даже если тест упал. Типично используется для закрытия соединений, удаления временных файлов, откатов транзакций.

**11.** Что произойдёт, если в двух `conftest.py` на разных уровнях папок объявлены фикстуры с одинаковым именем?

Эталон: pytest ищет фикстуры по иерархии директорий — фикстура из `conftest.py`, ближайшего к тесту (в его собственной папке или ниже по дереву), переопределяет одноимённую фикстуру из родительского `conftest.py`.

**12.** Как работает `@pytest.mark.parametrize` и зачем указывать `ids=`?

Эталон: `parametrize` запускает один и тот же тест несколько раз с разными наборами входных данных, каждый набор — отдельный тест в отчёте. `ids=` задаёт человекочитаемые имена для каждого набора вместо автогенерируемых (типа `test_x[0]`), что упрощает поиск причины падения в отчёте.

**13.** Чем `pytest.raises(SomeError)` отличается от обычного `raise SomeError` в коде теста?

Эталон: `raise` в тесте — это бросить исключение самому (например, для отладки), тест из-за него упадёт с ошибкой. `pytest.raises(SomeError)` — это context manager, который проверяет, что тестируемый код внутри блока действительно бросает `SomeError`; если исключение не возникло — тест провалится сам, если возникло другое исключение — тест тоже провалится из-за несовпадения типа.

**14.** Что такое маркер (marker) в pytest и зачем регистрировать кастомные маркеры в `pytest.ini`?

Эталон: маркер — метка на тесте (`@pytest.mark.regression`), позволяющая запускать тесты выборочно через `pytest -m regression`. Регистрация в `pytest.ini` (`markers`) избавляет от warning «unknown marker» и документирует, какие маркеры вообще существуют в проекте.

**15.** Как запустить только тесты с определённым маркером и только тесты, у которых в имени есть подстрока?

Эталон: `pytest -m regression` — по маркеру; `pytest -k "post"` — по подстроке в имени теста/файла/класса (можно комбинировать через `and`/`or`/`not`, например `-k "post and not delete"`).

**16.** Что делает `conftest.py` и почему его не нужно явно импортировать в тестовых файлах?

Эталон: `conftest.py` — специальный файл pytest, куда кладут фикстуры и хуки, общие для тестов в этой папке и подпапках. pytest автоматически подхватывает его по расположению в дереве директорий — явный `import` не нужен и не будет работать как обычный модуль.

### C. HTTP/API (8 вопросов)

**17.** Какая разница между GET и POST по смыслу использования?

Эталон: GET — получение данных, не должен менять состояние сервера (safe-метод), параметры обычно в query string, тело запроса не используется. POST — создание нового ресурса или действие с побочным эффектом, данные передаются в теле запроса.

**18.** Чем PUT отличается от PATCH?

Эталон: PUT — полная замена ресурса целиком (передаётся весь объект, отсутствующие поля считаются сброшенными/удалёнными). PATCH — частичное обновление, передаются только изменяемые поля, остальные остаются как были.

**19.** Что означает статус 204 и чем он отличается от 200?

Эталон: 200 — успешный запрос с телом ответа (обычно данные). 204 No Content — запрос успешен, но в ответе намеренно нет тела (типично для DELETE или PUT без возврата обновлённого объекта).

**20.** Чем 400 отличается от 422, если оба про «неверный запрос»?

Эталон: 400 Bad Request — общая ошибка синтаксиса/формата запроса (невалидный JSON, неверный Content-Type). 422 Unprocessable Entity — запрос синтаксически валиден, но не проходит бизнес-валидацию (например, email в правильном формате, но правило сервиса его отклоняет). Многие API на практике используют только 400 — это нормально, важно понимать саму разницу уровней.

**21.** Чем отличаются 401 и 404 с точки зрения того, что видит клиент?

Эталон: 401 Unauthorized — сервер понимает, о каком ресурсе речь, но клиент не аутентифицирован (нет/невалиден токен). 404 Not Found — ресурс с таким идентификатором не существует вообще, независимо от того, кто спрашивает. Иногда 404 используют намеренно вместо 401/403, чтобы не подсказывать атакующему, что ресурс существует.

**22.** Опишите порядок, в котором вы бы выстроили проверки для одного API-эндпоинта, от структуры до бизнес-логики.

Эталон: контракт (структура ответа — обязательные/опциональные поля, типы, вложенность) → статус-код (соответствует ли ситуации: 200/201/400/404 и т.д.) → тело/данные (сами значения, соответствие ожидаемому) → бизнес-логика (правильность расчёта, состояния) → негативные/граничные сценарии (невалидный вход, отсутствующие поля, границы).

**23.** Что имеет смысл проверять в API-тесте кроме статус-кода и тела ответа?

Эталон: заголовки ответа (Content-Type, кэш-заголовки), формат и текст сообщений об ошибках (не только код, но и понятность), при необходимости время ответа, и то, что запрос действительно вызвал ожидаемый побочный эффект (например, ресурс реально создался — можно перепроверить через GET).

**24.** Как бы вы тестировали эндпоинт создания ресурса (POST) с точки зрения негативных сценариев?

Эталон: отсутствие обязательного поля, неверный тип значения, пустая строка/null там, где не допускается, превышение допустимой длины/границ, дублирование уникального поля (конфликт 409), запрос без авторизации, невалидный формат (например email/телефон).

### D. Auth — authentication, authorization, JWT, access/refresh (12 вопросов)

**25. [ДОЛГ]** Из каких трёх частей состоит JWT-токен, в каком порядке?

Эталон: `header.payload.signature` — три части, разделённые точками. `header` — метаданные (алгоритм подписи, тип токена), `payload` — данные (claims: id пользователя, время выдачи/истечения и т.д.), `signature` — подпись, которой сервер проверяет, что токен не был изменён.

**26. [ДОЛГ]** JWT и пара access/refresh token — это одно и то же или разные уровни? Объясните разницу.

Эталон: это два разных уровня, их легко перепутать. JWT — это формат/структура одного токена (`header.payload.signature`). Access/refresh — это архитектурная схема из двух токенов разного назначения и срока жизни; сам access token часто (но не обязательно) реализован именно как JWT. То есть «из чего состоит JWT» — это не тот же вопрос, что «какие токены участвуют в сессии».

**27. [ДОЛГ]** Чем authentication отличается от authorization?

Эталон: authentication (аутентификация) — проверка того, **кто ты** (логин/пароль, SMS-код, токен подтверждают личность). Authorization (авторизация) — проверка того, **что тебе разрешено делать**, после того как личность уже подтверждена (доступ к конкретному ресурсу, роль, права).

**28. [ДОЛГ]** Что должен вернуть защищённый endpoint при отсутствующем токене и при валидном токене без нужных прав?

Эталон: без токена (или с невалидным/истёкшим) — 401 Unauthorized. С валидным токеном, но недостаточными правами/ролью — 403 Forbidden. С валидным токеном и достаточными правами — 200 (или соответствующий успешный код) и запрошенные данные.

**29.** Что такое access token и для чего он используется при каждом запросе?

Эталон: access token — короткоживущий токен, который клиент передаёт при каждом запросе к защищённым ресурсам (обычно в заголовке Authorization или в cookie), чтобы сервер подтвердил личность и права без повторного логина на каждый запрос.

**30.** Что такое refresh token и чем он отличается от access token по назначению и сроку жизни?

Эталон: refresh token — токен с более длительным сроком жизни; используется не для прямого доступа к ресурсам, а для получения нового access token, когда старый истёк — без повторной аутентификации логином/паролем.

**31. [ДОЛГ]** Опишите 3–4 сценария теста для refresh token.

Эталон: валидный refresh → выдаётся новый access token; истёкший refresh → отказ, требуется полный логин; невалидный/поддельный refresh → 401; повторное использование уже использованного refresh (reuse), если система это запрещает; logout/revocation — refresh должен перестать работать после выхода.

**32. [ДОЛГ]** Что должно произойти на сервере и на клиенте, когда access token истекает во время работы пользователя?

Эталон: сервер отклоняет запрос с истёкшим токеном (401). Клиент (если реализован refresh-flow) автоматически вызывает эндпоинт обновления с refresh token и получает новый access token, повторяя исходный запрос прозрачно для пользователя; если refresh тоже недействителен — пользователя перенаправляют на повторный логин.

**33. [ДОЛГ]** Опишите кейсы теста для авторизации (authorization) отдельно от кейсов логина.

Эталон: доступ с ролью, у которой есть права — успех; доступ с ролью без прав — 403; доступ без токена вообще — 401; доступ к чужому ресурсу (например чужому профилю по id) при валидном токене — обычно 403/404 в зависимости от политики. Это не про ввод пароля/SMS — это про то, что разрешено уже аутентифицированному пользователю.

**34.** Опишите последовательность аутентификации через SMS-код от начала до выдачи токена.

Эталон: пользователь вводит номер телефона → сервер отправляет SMS с одноразовым кодом → пользователь вводит код → сервер проверяет код и, если верен, считает пользователя аутентифицированным → выдаёт токен(ы) (например JWT через cookie или в теле ответа).

**35.** Если JWT хранится в cookie, а не в заголовке Authorization — что это меняет для тестирования?

Эталон: сам факт «это JWT» не меняется — меняется способ передачи. Нужно проверять атрибуты cookie (HttpOnly, Secure, SameSite), что cookie реально проставляется после логина и передаётся браузером автоматически на защищённые запросы, и что при отсутствии/удалении cookie защищённый endpoint отдаёт 401 — так же, как при отсутствии заголовка в схеме с Authorization header.

**36.** Какие кейсы вы бы проверили для собственно логина (до выдачи токена), отдельно от токенов?

Эталон: валидные учётные данные → успех; неверный пароль/код → отказ (обычно 400/401, не 500); несуществующий пользователь; превышение попыток (если есть lockout/rate limit); пустые/некорректно оформленные поля ввода (телефон/email/пароль).

### E. Моки: unittest.mock vs Mountebank/WireMock (5 вопросов)

**37. [ДОЛГ]** Чем `unittest.mock`/`patch` отличается от Mountebank/WireMock по уровню тестирования?

Эталон: `unittest.mock`/`patch` подменяет объект или функцию прямо внутри процесса теста (в памяти), без реального сетевого вызова — это уровень юнит-теста, проверяет только «моя функция вызвала зависимость правильно». Mountebank/WireMock — отдельный процесс, который реально слушает порт и отвечает на настоящие HTTP-запросы — это уровень интеграционного теста / service virtualization, проверяет весь сетевой цикл запрос-ответ.

**38.** В каком случае вы бы выбрали `unittest.mock`, а в каком — Mountebank или аналог?

Эталон: `unittest.mock` — когда тестируется одна функция/класс в изоляции и не важен реальный HTTP-протокол (быстро, не нужна инфраструктура). Mountebank/WireMock — когда важно проверить полный контракт между сервисами, смоделировать задержки, обрывы, конкретные коды ошибок от внешнего сервиса, которые сложно или опасно воспроизвести на реальном стенде.

**39.** Расскажите, как вы на практике использовали mock-сервис (Mountebank или аналог) в своих тестах.

Эталон: поднимается mock-сервис, который слушает реальный порт; заранее настраивается имитация (stub) — на какой запрос какой ответ, статус, задержку отдать; тестируемый сервис в тестовом окружении ходит в этот mock как в настоящий бекенд по другому адресу; это позволяет детерминированно воспроизводить граничные случаи (500, таймаут внешнего сервиса), которые сложно спровоцировать на реальном стенде.

**40.** Что делает `patch("module.requests.get")` и почему путь указывается там, где функция **используется**, а не там, где она **определена**?

Эталон: `patch` временно заменяет объект по указанному пути атрибута на mock на время выполнения тестового блока/функции, а затем возвращает оригинал обратно. Путь важен, потому что `patch` подменяет имя в том namespace, где оно импортировано и используется (в тестируемом модуле), а не в модуле, где функция исходно определена — если патчить не то место, тестируемый код продолжит использовать оригинал.

**41.** Зачем вообще может понадобиться `patch` на реальный внешний API в тесте, если можно просто вызвать его напрямую?

Эталон: если нужно проверить обработку конкретной ошибки (например 500 или таймаут), а живой сервис её физически не отдаёт по запросу — единственный надёжный способ спровоцировать этот путь кода — подменить вызов и вручную задать нужный побочный эффект/ответ.

### F. Сильные стороны — Pydantic, независимый expected, стек (4 вопроса)

**42.** Расскажите на примере, как вы валидировали структуру API-ответа на своём проекте.

Эталон: через Pydantic-схему — описывается модель с обязательными и опциональными полями, типами (включая nullable, списки, вложенные объекты); при разборе ответа Pydantic сам бросает ошибку валидации, если структура не совпадает — это заменяет вручную написанные проверки «есть ли ключ, тот ли тип».

**43.** Расскажите на примере сложного бизнес-расчёта, который вы проверяли в тестах, и как считали ожидаемый результат.

Эталон: на примере графика платежей — проверялись сумма, количество траншей, процент, срок и производные параметры. Ключевой момент: ожидаемый результат не хардкодился заранее, а рассчитывался независимо в отдельном helper/check-функции по той же бизнес-формуле, и затем сравнивался с фактическим ответом API — это защищает тест от совпадения двух одинаково неверных чисел.

**44.** Почему считать expected-результат отдельным независимым способом (а не хардкодить заранее посчитанное число) — это хорошая практика?

Эталон: если один раз вручную посчитать число и вписать его в тест, тест не проверяет формулу — он проверяет совпадение с конкретным случаем. Независимый расчёт (helper с той же логикой, но отдельно от продуктового кода) ловит регрессии в самой формуле и легко переносится на новые входные данные через `parametrize`, без ручного пересчёта каждый раз.

**45.** Какой стек инструментов вы используете для API-автоматизации и как они сочетаются друг с другом?

Эталон: Python + pytest как раннер и организация тестов; `requests` для HTTP-вызовов; Pydantic-схемы для валидации структуры ответа; параметризация pytest для прогонки наборов данных; Allure для отчётности. На интеграционном уровне — Mountebank для имитации внешних сервисов.
